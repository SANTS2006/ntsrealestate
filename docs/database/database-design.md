# Database Design — Neon PostgreSQL

## 1. Conventions

- Primary keys: `uuid` (`gen_random_uuid()`, via `pgcrypto`/native `gen_random_uuid()` on
  Postgres 13+, which Neon supports).
- Money: `NUMERIC(14,2)` — never `float`/`double`.
- Timestamps: `TIMESTAMPTZ`, `created_at`/`updated_at` on every table, `updated_at`
  maintained by a trigger (or Prisma `@updatedAt`).
- Flexible/rarely-queried metadata: `JSONB` (e.g. `organizations.settings`,
  `leases.terms`) — never used for data that needs relational integrity or indexing beyond a
  GIN index.
- Every organization-owned table has `organization_id UUID NOT NULL REFERENCES
  organizations(id)`, indexed.
- Enums are modeled as Postgres `ENUM` types (via Prisma `enum`) for status fields
  (`lease_status`, `unit_status`, `invoice_status`, `payment_status`,
  `maintenance_priority`, `maintenance_status`, `user_status`) — invalid states are
  rejected at the database level, not just application level.

## 2. Schema

The authoritative schema is `server/prisma/schema.prisma` (Prisma is the chosen ORM — see
§3). It implements every entity listed in the master requirements (organizations, users,
roles, permissions, role_permissions, user_roles, sessions, properties, buildings, units,
owners, tenants, leases, invoices, payments, expense_categories, expenses, vendors,
maintenance_requests, work_orders, inspections, documents, notifications, audit_logs).

## 3. ORM choice: Prisma

Prisma is used because:
- First-class Neon/serverless support via `@prisma/adapter-neon` + `@neondatabase/serverless`
  (WebSocket-based driver, works over Neon's pooled connection without needing a persistent
  TCP pool from a serverless-style host).
- Type-safe query building eliminates an entire class of injection bugs by construction.
- Native migration tooling (`prisma migrate`) that works cleanly against Neon.
- Mature ecosystem, straightforward transaction API (`prisma.$transaction`) used throughout
  the service layer for multi-step financial/lease operations.

## 4. Connection strategy (Neon-specific)

Neon exposes both a **pooled** (PgBouncer, transaction mode) and **direct** connection
string. Strategy:

| Use case | Connection |
|---|---|
| Runtime app queries (`DATABASE_URL`) | Pooled — high connection churn from serverless-style hosting is expected |
| `prisma migrate` / schema changes (`DIRECT_URL`) | Direct — migrations need a session-mode connection, which PgBouncer transaction pooling doesn't support |

`schema.prisma` declares both `url` and `directUrl` on the datasource block accordingly.
Because pooled/transaction-mode connections can't safely carry `SET LOCAL` session state
across statements, organization scoping is enforced at the query-parameter level (explicit
`WHERE organization_id = $1` on every query — see authorization.md §4), not via a
session-variable-based RLS context, until/unless a direct-connection RLS rollout (staged
per authorization.md §5) is undertaken.

## 5. Key constraints enforcing business rules

- `units`: a **partial unique index** on `(unit_id) WHERE status = 'active'` in `leases`
  prevents two simultaneously-active leases on the same unit at the database level (in
  addition to the service-layer transaction check).
- `invoices`/`payments`: `balance` is a generated/derived value recomputed inside the same
  transaction that inserts a payment — never trusted from client input.
- `documents`: `(cloudinary_public_id)` unique — prevents duplicate metadata rows pointing
  at the same asset.
- Foreign keys use `ON DELETE RESTRICT` by default for financial/audit-linked tables (you
  cannot delete a tenant with existing leases/invoices out from under the data), and
  `ON DELETE CASCADE` only for genuinely dependent child rows (e.g. `role_permissions` rows
  when a role is deleted).

## 6. Indexing

Composite/singleton indexes are added for every foreign key plus the query patterns called
out in the requirements: `organization_id`, `email` (unique per org), `property_id`,
`tenant_id`, `unit_id`, `lease_id`, `invoice_id`, `status`, `created_at`, `payment_date`,
`due_date`. See `schema.prisma` `@@index`/`@@unique` blocks — indexes live next to the model
they belong to rather than in a separate file, so they stay in sync with the schema.

## 7. Migrations vs seeds

- `server/prisma/migrations/` — versioned, generated by `prisma migrate dev` /
  `prisma migrate deploy`. Never hand-edited after being applied anywhere.
- `database/seeds/` — development-only demo data (fake organizations, users across every
  role, sample properties/leases/invoices). Never run against production; guarded by a
  `NODE_ENV !== 'production'` check in the seed script itself.
