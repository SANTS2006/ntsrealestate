# Deploying for free (no domain required)

This app deploys as **one Render.com free Web Service** that serves both the
API and the built React app from the same URL — e.g.
`https://ntsrealestate.onrender.com`. Frontend and backend sharing one
origin isn't just convenient: the session cookie is `SameSite=Lax`, which
only survives cross-site requests when frontend and backend genuinely share
an origin. Splitting them across two different hosts (a static host for the
frontend, a separate one for the API) would silently break login unless the
cookie/CORS setup were reworked — this setup avoids that entirely.

Render's free tier requires no credit card for a Node web service. The one
trade-off: it sleeps after ~15 minutes with no traffic, so the first request
after a quiet period takes 30–50 seconds to wake back up. Everything after
that is normal speed.

## What you'll need before starting

- A GitHub account (to host the repo Render deploys from)
- A Render account (render.com — free, sign up with GitHub for the smoothest
  connection step)
- The Neon database you've already been using in development (or a fresh
  Neon project — either works; reusing the dev one is simplest and still
  free)
- Your existing Cloudinary and Brevo API keys (same ones already in
  `server/.env` locally — reuse them, no need to create new accounts)

## 1. Push the code to GitHub

If this hasn't happened yet, create an empty repository on GitHub (no
README/`.gitignore` — this repo already has both), then:

```bash
git remote add origin https://github.com/<your-username>/<repo-name>.git
git branch -M main
git push -u origin main
```

## 2. Create the Render Blueprint

1. Log into Render → **New** → **Blueprint**.
2. Connect your GitHub account and pick this repo. Render reads
   [`render.yaml`](../../render.yaml) in the repo root automatically and
   proposes one Web Service (`ntsrealestate`) on the free plan.
3. Click through — Render will ask you to fill in every environment
   variable marked as a secret before the first deploy. See the table below
   for where each value comes from.

## 3. Environment variables

| Variable | Where it comes from |
|---|---|
| `DATABASE_URL` | Neon dashboard → your project → **Connection string** (pooled, the one with `-pooler` in the host) |
| `DIRECT_URL` | Neon dashboard → same project → the **non-pooled** connection string |
| `MFA_ENCRYPTION_KEY` | Generate locally: `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"` |
| `CLOUDINARY_CLOUD_NAME` / `CLOUDINARY_API_KEY` / `CLOUDINARY_API_SECRET` | Cloudinary dashboard, or copy from your local `server/.env` |
| `BREVO_API_KEY` | Brevo → Settings → SMTP & API → API Keys, or copy from local `server/.env` |
| `EMAIL_FROM_ADDRESS` / `SUPPORT_EMAIL` | Same values you use locally |
| `SESSION_SECRET`, `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET` | Auto-generated by Render (`generateValue: true` in `render.yaml`) — nothing to do |
| `CLIENT_URL`, `CORS_ORIGINS` | **Leave blank for now** — see step 4 |

## 4. First deploy, then set the URL-dependent variables

Render won't know the service's public URL until after the first deploy.

1. Let the first deploy run (it will build, and the app will start — CORS
   will just be misconfigured until you finish this step, which is fine).
2. Once deployed, copy the URL Render shows you, e.g.
   `https://ntsrealestate.onrender.com`.
3. Go to the service's **Environment** tab and set:
   - `CLIENT_URL` = that exact URL (no trailing slash)
   - `CORS_ORIGINS` = that exact URL (same value — it's a comma-separated
     list, but you only have one origin)
4. Save — Render redeploys automatically with the correct values.

## 5. Verify

Visit the URL. You should land on the login page over HTTPS. Register a new
account (or use an existing one, if you pointed at your dev database) and
confirm the dashboard loads, a page refresh doesn't log you out, and
uploading a document / receiving an email still works.

## Redeploying after future changes

Push to the connected branch (`main`) — Render redeploys automatically. No
manual steps needed unless a schema migration was added, which
`deploy:migrate` (wired into the build command) applies on every deploy
automatically.
