# Backup & Recovery

Platform admin → **Backup & recovery**. Everything here is restricted to signed-in **platform admins** (a separate identity from any company's users).

## How it works

| Step | What happens |
| --- | --- |
| Start | A row is inserted in `backups` with status `RUNNING`. A partial unique index (`backups_one_active`) allows only **one** running backup across all server instances, so two instances can never both back up. |
| Dump | One `REPEATABLE READ`, read-only transaction over a direct connection → a consistent snapshot while the app keeps writing. Tables are written in foreign-key order as gzipped lines `table⇥row-json`, with a header (schema version, columns) and a footer (row counts). No `pg_dump` binary is needed. |
| Encrypt | AES-256-GCM with `BACKUP_ENCRYPTION_KEY`. The authentication tag covers the whole file: damage or tampering fails to decrypt. Production refuses to create an unencrypted backup. |
| Store | Via `BackupStorageProvider`: `local` (development) or `s3` (any S3-compatible bucket). Storage keys are generated by the server; nothing from a request is used as a path. Files are never in a public/static folder. |
| Verify | The stored copy is re-read: exists, non-empty, size and **SHA-256** equal to the record, decrypts, every row parses, every table's count equals the dump's. Only then `verification = VERIFIED`. **A backup is a recovery point only when it is `COMPLETED` and `VERIFIED`.** |
| Retain | After each verified backup, old ones are deleted by policy (below). |

Recorded per backup: id, type (`AUTOMATIC` / `MANUAL` / `PRE_RESTORE`), status, verification, size, checksum, encrypted, storage provider, table/row counts, schema migration, who started it, error, timestamps. Storage keys are kept server-side and never returned by the API.

## Schedule

* `BACKUP_SCHEDULE` (default `02:00` UTC) — one automatic backup per day.
* Every server instance runs a one-minute check, but the database's one-running-backup rule means **only one instance actually runs it**. If a day's backup fails it is retried after 30 minutes, up to 3 attempts. If the server was down at 02:00 the backup runs as soon as it is back (catch-up).
* A job whose server died stops sending heartbeats; after 10 minutes it is marked `FAILED` and the lock is released.
* **Free-tier hosts sleep.** An in-process timer cannot run while the instance is asleep. Add an external scheduler that calls the web service once a day (Render Cron Job, GitHub Actions, any cron):

  ```
  curl -X POST https://<your-host>/api/v1/internal/backups/run -H "X-Cron-Secret: $BACKUP_CRON_SECRET"
  ```
  The call wakes the instance and runs the backup only if one is due, so calling it more often is harmless.

## Retention

Policy (editable by platform admins; defaults from `BACKUP_RETENTION_COUNT` / `BACKUP_RETENTION_DAYS`): keep the **newest N** verified backups **and** anything younger than **D days**. Pre-restore safety backups are kept for D days and do not count toward N. Never deleted, whatever the policy: the newest valid backup, the only valid backup, any backup an active restore is using. Failed rows are kept as history. Manual delete follows the same guards.

## Restore

Only platform admins. Always three deliberate steps, then a background job:

1. **Choose** a backup (must be `VERIFIED`). `POST /backups/restores/prepare` re-checks it and returns a 5-minute signed token bound to that admin and backup, plus the warning text.
2. **Read** the warning: *you are about to restore the database to the state captured on …; data created after this backup may be lost.*
3. **Confirm**: type `RESTORE DATABASE` **and re-enter your password**. Wrong phrase, wrong/expired token or wrong password → refused and audited.

The job (`backup_restores.status`): `pending → preparing → backing_up_current_database → restoring → verifying → completed | failed`.

* *preparing* re-verifies the chosen backup.
* *backing_up_current_database* creates and verifies a `PRE_RESTORE` backup. If that fails, nothing is restored.
* *restoring* is **one database transaction**: compatibility checks (same schema migration, same tables and columns), `TRUNCATE`, reinsert in dependency order.
* *verifying* counts every table **inside the same transaction**; `COMMIT` happens only if all counts equal the backup's. Any error rolls back and the live data is exactly as it was (`rolledBack: true`).

Not touched by a restore: sessions (people stay signed in), the backup/restore records themselves, idempotency keys, migration history. If the platform admin who restores did not exist in the backup, their next request will be signed out.

Writes from the app queue behind the restore's table locks and may time out while it runs. For a large database, switch on **Maintenance** (Platform admin → Maintenance) first.

### If something goes wrong

| Situation | Action |
| --- | --- |
| Restore shows `failed` | Read the message. The database is unchanged. Fix the cause (usually a schema mismatch) and retry. |
| Restore finished but the result is wrong | Restore the `PRE_RESTORE` backup listed just before it in the history — that is the state from immediately before. |
| Server died mid-restore | The transaction rolled back when the connection dropped. After 10 minutes the record shows `failed`; the database is unchanged. |
| Backups all `FAILED` | Check `BACKUP_STORAGE` credentials and `BACKUP_ENCRYPTION_KEY`; the error is shown per row and in the audit log. |
| Lost the encryption key | Encrypted backups cannot be read by anyone. **Store the key in two safe places outside the server** (password manager + sealed note). |

### Disaster recovery (database or host lost)

1. Provision a new database; deploy the same code version (`npm run deploy:migrate` creates the empty schema at the same migration).
2. Set the same `BACKUP_ENCRYPTION_KEY` and storage credentials, create a platform admin (`server/scripts/createPlatformAdmin.js`).
3. In Backup & recovery pick the latest valid backup and restore it. (If the console cannot start, download the `.rbk` file from the bucket, and restore with `restoreFromFile` in `server/src/services/backup/engine.js`.)
4. Check the app, then re-enable the daily schedule.

## Targets (assumptions)

* **RPO (data you can lose): up to 24 hours** with one daily backup. Take a manual backup before risky changes. For an RPO of minutes, also enable the database provider's point-in-time recovery (Neon: history retention) — complementary, not replaced by this.
* **RTO (time to be running again): about 15–30 minutes** for a database of this size (a backup of ~2,000 rows takes seconds; restore time grows roughly linearly with rows), plus the time to provision a new database in a full disaster.
* Assumes the storage bucket and the encryption key survive, and that the bucket is in a different failure domain from the app host.

## Audit trail

`PlatformAuditLog` actions: `BACKUP_CREATED`, `BACKUP_VERIFIED`, `BACKUP_VERIFICATION_FAILED`, `BACKUP_FAILED`, `BACKUP_DELETED`, `BACKUP_DOWNLOADED`, `BACKUP_POLICY_CHANGED`, `RESTORE_PREPARED`, `RESTORE_DENIED`, `RESTORE_STARTED`, `RESTORE_COMPLETED`, `RESTORE_FAILED`, `RESTORE_ROLLBACK`. Each records the admin, target backup, time, result/reason and IP. The log is append-only through the application (no edit/delete API).

## Admin API

All under `/api/v1/platform-admin`, platform-admin session required, `X-CSRF-Token` on writes. Errors use `{ success:false, error:{code,message}, requestId }`.

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/backups/status` | health (`healthy`/`stale`/`no_valid_backup`), latest and latest valid backup, next scheduled run, policy, running backup, active restore, storage/encryption flags |
| GET | `/backups?page&pageSize&type&status` | paginated history |
| GET | `/backups/:id` | one backup (poll while `RUNNING`) |
| POST | `/backups` | manual backup → `202`, returns the new `RUNNING` row; `409` if one is running or a restore is active |
| POST | `/backups/:id/verify` | re-verify a stored backup |
| GET | `/backups/:id/download` | the encrypted `.rbk` file (audited, rate-limited) |
| DELETE | `/backups/:id` | guarded delete (`409` for newest/only valid or in use) |
| GET / PUT | `/backups/policy` | `{retentionCount, retentionDays}` |
| POST | `/backups/restores/prepare` `{backupId}` | validate, returns `{backup, token, expiresAt, requiredPhrase, warning}` |
| POST | `/backups/restores` `{backupId, token, confirmation, password}` | start → `202` with the restore row |
| GET | `/backups/restores?page&pageSize` | restore history |
| GET | `/backups/restores/:id` | progress: `status`, `inProgress`, `errorMessage`, `rolledBack`, `verification` |
| POST | `/api/v1/internal/backups/run` | external scheduler; header `X-Cron-Secret`; runs a backup only if one is due |

## Environment variables

`BACKUP_STORAGE` (`local`\|`s3`), `BACKUP_LOCAL_DIR`, `BACKUP_ENCRYPTION_KEY` (64 hex), `BACKUP_SCHEDULE` (`HH:MM` UTC), `BACKUP_SCHEDULER_ENABLED`, `BACKUP_RETENTION_COUNT`, `BACKUP_RETENTION_DAYS`, `BACKUP_CRON_SECRET`, `S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`. Placeholders are in `.env.example`; real values only in the host's secret store.

## Known limits

* The dump streams to disk and to the bucket (flat memory), but the restore of a very large database holds table locks for its whole duration; use maintenance mode.
* The S3 provider is implemented against the S3 API but has not been exercised against a real bucket in this repository's tests.
* Bucket-side protections (versioning/object lock, a separate account, lifecycle rules) are configured in the storage provider, not in this code.
